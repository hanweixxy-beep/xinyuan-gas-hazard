# 鑫远项目长期开发维护建议

这是一份流程建议，未安装插件、未更改项目自动执行权限，也未配置新的云端服务。

## 结论

继续用日常语言描述需求完全可行。每个需求应转换成可追踪的业务规则、验收标准、版本变更和测试证据，并长期保存在项目中。建议采用适度的 Superpowers 开发流程，加上项目自己的版本、发布及运维制度。

Superpowers 官方仓库的流程涵盖需求讨论、方案、隔离开发、任务计划、测试、审查和分支收尾，适合作为 AI 开发助手的工作规范。单靠安装一个技能不能证明系统已经具备可靠的备份、监控、回退、持续运行或跨会话的项目知识。

## 每次需求的交付流程

| 阶段 | 你需要做什么 | 开发工作应留下什么 |
| --- | --- | --- |
| 需求 | 描述目标、使用场景和不满意之处 | 需求编号、业务规则、范围和明确的验收条件；重要歧义一次说明 |
| 方案 | 对涉及业务取舍的方案作决定 | 影响范围、数据兼容、风险和回退方案；普通小改直接执行 |
| 开发 | 无需掌握代码 | 独立的变更记录、必要的测试、与需求对应的修改 |
| 验收 | 在手机/后台体验关键操作 | 自动检查结果、真机/浏览器证据、尚未验证项，明确区分构建和实测 |
| 发布 | 对会影响业务的发布时机作决定 | 版本号、发布说明、备份位置、部署结果和回退入口 |
| 运维 | 接收需要处理的异常 | 可操作的告警、故障记录、修复与复盘、定期恢复演练 |

## 优先补齐的项目基础

1. **可恢复的版本基线**：先梳理现有累计修改和线上版本对应关系，再建立能复现、能回退的代码版本，避免把无关修改混成一次发布。
2. **项目说明和工作规则**：简短、准确的 `AGENTS.md`，注明真实代码位置、构建检查方式、验收定义、保护生产数据及表格范围；详细内容分放架构、接口、数据字典和发布手册。
3. **需求与问题清单**：先用仓库内文件或 GitHub Issues 即可，记录待办、处理中、已验证、已发布。不必一开始引入多个项目管理平台。
4. **自动验证**：按改动运行后端权限/分页/导出测试及 Android 规则测试、构建；后续再接入每次变更自动运行的检查。照片、导出、分页、整改和账号权限列入核心回归流程。
5. **隔离测试环境**：与生产数据分开，使用测试账号和样本，完成手机与管理后台验收后再发布。
6. **发布和回退手册**：明确代码、数据库变更、APK 签名、版本号与升级兼容关系；上线后核查关键服务和核心操作。
7. **运维保障**：数据库、照片和配置分别备份并定期实际恢复；检查网站可用性、错误、证书、磁盘、导出队列和备份失败。告警需要有接收人和处置步骤。

建议先完成版本基线、项目规则、验收清单这三件事，再逐步增加自动化。所有制度都服务于减少漏项和返工，不要求你每次填写长文档。

## 本次提醒需求的验收示例

需求：未整改记录首次满 3 天提醒，之后每 3 天重复，完成整改后停止。

对应验收：满 3 天才提醒；多条汇总；点击进入待整改列表；完成后停止；不同账号隔离；超过 1000 条不遗漏；不允许通知时不消耗次数；断网和省电限制有明确说明。
