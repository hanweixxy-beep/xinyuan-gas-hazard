# Windows 与 Mac 交替开发

## 当前边界

两台电脑各有一份本地源码，用同一个现有私有 GitHub 仓库同步。代码提交、GitHub 推送、手机安装、服务器部署是四件不同的事，不能互相代替。聊天记录不作为源码或业务规则的唯一保存位置；新对话从 AGENTS.md 与 PROJECT_STATE.md 接续即可。

首次 Windows 基线同步完成前，Mac 克隆只能拿到旧版。当前准备材料本身不代表已经提交、推送或部署。

## 只用记住这套顺序

1. 开工：确认另一台已经收工并推送；查看本机是否有未提交内容。有的话先保存、核对，不覆盖。
2. 同步：干净工作区执行 git pull --ff-only；有冲突或分叉就停下来保留两边工作，交由开发助手说明差异。
3. 开发：只在当前这台继续同一任务。日常小任务沿用 main；涉及多人或同时开发时另建分支和评审，不在两台上各自改同一份任务。
4. 验证：运行改动相关的测试和真实手机/浏览器验收；在 PROJECT_STATE.md 记录结果与没测到的部分。
5. 收工：核对文件、敏感信息、版本说明，按授权提交并推送；再确认远端 main 与本机提交号一致，最后换电脑。

提交保存在当前电脑；推送完成，另一台才能获取。若未联网或推送失败，要明确告诉用户“本机已保存，尚未交接”。

## 开工与收工核对命令

以下在源码仓库根目录运行，不在聊天 outputs/work 目录运行：

~~~text
git status --short --branch
git log -1 --oneline
node tools/collab-check.cjs
~~~

核对工具只读检查，不自动拉取、提交、推送或部署。首次准备期间可用 --offline 跳过远端检查；不能把离线通过当作已同步。退出码 2 表示尚不能交接，请看其列出的原因。

## Mac 首次接手

1. 用有权限的 GitHub 账号克隆现有仓库到新的本地目录，不覆盖已有文件夹。
2. 核对 Windows 交付的完整提交号；在 Mac 上运行 git rev-parse HEAD，结果须一致。若旧代码仍是 87af737，表示首次基线同步尚未完成。
3. 按 DEVELOPMENT_ENVIRONMENT.md 配置工具和本地开发环境。Mac 的 SDK 路径与签名属性文件须独立生成，不能照抄 C 盘路径。
4. 在 Codex 中打开克隆出的真实 Git 根目录，读取 AGENTS.md 与 PROJECT_STATE.md 后继续。
5. 先做不写正式业务的检查、构建与隔离样本测试；实际连接手机并安装成功后才算真机验收。不要用部署脚本来验证 Mac 是否能开工。

## 密钥、数据与恢复

- Git 同步源码、结构迁移、无密码模板、项目状态；不携带服务器私钥、发布签名、生产 .env、客户照片或数据库。
- 开始源码开发只需要 GitHub 访问和开发工具。签名用于正式 APK，服务器私钥用于批准后的维护，均按需要从用户自己的安全备份转移，不通过聊天发送密码。
- 原来的 Windows 先保留完整可用环境。Mac 验收完成前不清理或重置它。
- 首次准备保存了完整已提交 Git 历史 bundle 和可纳入版本的工作文件快照；这不是数据库、照片或签名备份，也不能替代异地备份。
- 回退先检查具体差异，优先通过新的恢复提交保留历史；禁止未经授权 reset --hard、clean -fd、force push 或覆盖生产数据库。
